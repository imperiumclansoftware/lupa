2. Authentification et sessions

MécanismeMise en œuvre
Hachage des mots de passeArgon2id (algorithm: sodium), rehachage automatique des anciens bcrypt (PasswordUpgraderInterface).
Politique des mots de passe12 à 4096 caractères, robustesse « moyenne » au moins (PasswordStrength), refus des mots de passe divulgués sur Rémus (NotCompromisedPassword, k-anonymat) ; Security/PasswordPolicy.php.
Limitation des tentativeslogin_throttling : 5 essais par 15 minutes (par identifiant et adresse IP, et par adresse IP) ; les codes de double authentification faux sont comptés.
Adresse IP fiableAucun proxy cru par défaut (TRUSTED_PROXIES=127.0.0.1) : un client ne peut pas falsifier X-Forwarded-For pour contourner la limitation.
Double authentificationTOTP (30 s, 6 chiffres), activation confirmée par un code et mot de passe redemandé ; 10 codes de secours de 50 bits, conservés en SHA-256, à usage unique ; 5 codes faux ferment la session (Security/TwoFactorHandler.php).
SessionsCookie HttpOnly, SameSite=Strict, Secure et préfixe __Host- derrière un proxy HTTPS déclaré ; use_strict_mode ; identifiant renouvelé à la connexion ; fichiers de session dans le volume.
Anti-CSRFJeton aléatoire de 256 bits en session, renvoyé par l'interface dans l'en-tête X-XSRF-TOKEN et comparé en temps constant (Security/CsrfSubscriber.php).
InstallationCode d'installation de 12 caractères aléatoires, affiché dans les journaux du serveur, conservé en SHA-256, à usage unique, valable tant qu'aucun compte n'existe.

3. Autorisations

  • Refus par défaut : access_control exige un rôle sur toute l'API ; seules la connexion, la session et l'installation sont publiques.
  • Hiérarchie : lecteur < opérateur < administrateur. Toute écriture sur l'API exige au moins le rôle opérateur ; les comptes, réglages, liste noire, dépôts sources, suppression de listes, clés de confiance et l'approbation d'un collecteur exigent le rôle administrateur (#[IsGranted]).
  • Garde-fous : un administrateur ne modifie ni son propre rôle ni ne supprime son compte ; il reste toujours au moins un administrateur.
  • Tests : chaque action d'écriture est essayée avec les trois rôles dans les tests fonctionnels.
  • Registres de Romulus : en lecture seule et sans authentification (décision ADR 0001) ; docker push est refusé.

Les outils tiers ne lancent aucun script d'installation : npm avec --ignore-scripts, Composer avec --no-scripts --no-plugins. Exception : les modèles de framework exécutent le générateur officiel (Angular CLI, Nest CLI), voir le risque R4.

5.2 À l'import (Romulus)

La liste noire voyage dans le manifeste signé ; elle met en quarantaine les versions interdites, même importées auparavant, sur tous les registres de Romulus. Un contrat de format, testé en continu, garantit que Romulus relit exactement ce que Rémus produit.

7. Journalisation, conteneurs et développement

  • Audit : canal dédié, au format JSON sur la sortie d'erreur ; un processeur Monolog masque mots de passe, jetons, cookies, en-têtes Authorization et identifiants dans les URL avant écriture. Les dépréciations techniques ne sont pas journalisées en production.
  • Conteneurs : utilisateur sans privilège (UID de l'hôte, ou root sans privilège de Docker rootless), toutes les capabilities retirées sauf CHOWN, DAC_OVERRIDE, FOWNER (effectives seulement en rootless), no-new-privileges, système de fichiers en lecture seule, clés USB montées en lecture seule sur Romulus.
  • Mises à jour : images Alpine mises à jour à la construction (apk upgrade) ; Dependabot hebdomadaire avec délai de sept jours pour les nouvelles versions.
  • Intégration continue (bloquante) : PHPStan au niveau maximal avec ligne de base, PHP-CS-Fixer, PHPUnit (≈ 200 tests dont contrôle d'accès par rôle, contrat du bundle, rollback d'export), ESLint avec règles de sécurité, Prettier, composer audit, npm audit, Semgrep (PHP, TypeScript, OWASP Top 10), gitleaks, Trivy sur les images (HIGH et CRITICAL corrigibles) ; actions GitHub épinglées par empreinte de commit.
  • Décisions : chaque écart assumé aux règles de sécurité est documenté dans un ADR (docs/adr).

8. Failles et risques résiduels

Aucune vulnérabilité connue et exploitable n'est ouverte à la date du document. Les éléments ci-dessous sont des risques résiduels : limites de conception, choix assumés ou dépendances à la configuration de l'exploitant. La criticité combine l'impact et la probabilité dans un déploiement conforme à la documentation.

NiveauSignification
CritiqueCompromission probable du réseau isolé ; à traiter avant toute mise en service (aucun risque de ce niveau à ce jour).
ÉlevéeImpact grave et probabilité réelle ; mesures compensatoires attendues de l'exploitant.
MoyenneImpact important mais conditions d'exploitation restrictives, ou impact limité et probable.
FaibleImpact limité ou exploitation peu vraisemblable ; à suivre.

R1 — Paquet malveillant ou compromis collecté et servi Élevée

Impact critique · probabilité moyenne · nature de la fonction

Description. Lupa garantit que Romulus sert exactement les fichiers publiés par les registres, mais pas qu'ils sont sains. Aucun antivirus ni analyse comportementale n'est appliqué ; les alertes OSV.dev ne couvrent que les vulnérabilités connues de npm, Python et Composer.

Scénario. Un attaquant publie une version piégée d'un paquet populaire (compte de mainteneur volé, typosquattage, dépendance confuse). Une liste en contrainte large la collecte ; elle est exportée et installée par les postes du réseau isolé, où son code s'exécute (scripts d'installation npm, setup.py, conteneur Docker…).

Risques encourus. Exécution de code sur les postes ou serveurs du réseau isolé, vol de données, porte dérobée persistante : exactement ce que l'isolement devait empêcher.

En place. Sommes et signatures des registres, liste noire et quarantaine propagées par bundle, alertes OSV, historique des exports. Recommandé. Versions précises pour les projets sensibles, délai avant de collecter une version toute récente, revue de la page Sécurité avant export, analyse antivirale et scanner d'images (Trivy, Grype) sur les bundles à l'entrée de la zone isolée.

R2 — Interfaces et registres servis en HTTP par défaut Élevée

Impact critique · probabilité moyenne · configuration (ADR 0002)

Description. Les images écoutent en HTTP ; le HTTPS est assuré par un reverse proxy que l'exploitant met en place. Sans lui, mots de passe, cookies de session et paquets circulent en clair.

Scénario. Un attaquant présent sur le réseau (poste compromis, usurpation ARP) intercepte une connexion à l'administration ou modifie à la volée un paquet servi par Romulus à un poste ; pip, apt et Docker ne vérifient pas tous une empreinte de bout en bout.

Risques encourus. Vol de session ou de mot de passe administrateur ; installation d'un paquet modifié sur un poste.

En place. Cookies __Host- et Secure dès qu'un proxy HTTPS est déclaré, HSTS, index apt et RPM signés par Romulus, digests Docker. Recommandé. Reverse proxy HTTPS avec certificat de la PKI interne, PUBLIC_URL et TRUSTED_PROXIES renseignés ; à défaut, filtrer l'accès réseau aux seuls postes autorisés.

R3 — Compromission du serveur Rémus et de sa clé de signature Élevée

Impact critique · probabilité faible · conception

Description. Toute la confiance de Romulus repose sur la clé privée de Rémus, stockée en clair (fichier protégé par les droits système) dans le volume du serveur connecté à Internet.

Scénario. Un attaquant obtient l'accès au serveur Rémus (faille du système, du conteneur, ou R4) et copie la clé ; il fabrique un bundle signé contenant des paquets piégés, accepté par Romulus.

Risques encourus. Introduction arbitraire de logiciels dans le réseau isolé, sans alerte.

En place. Conteneur sans privilège, en lecture seule ; empreinte comparée à l'approbation ; numéros de séquence ; révocation par retrait de la clé sur Romulus. Recommandé. Serveur Rémus dédié, durci et surveillé ; sauvegarde chiffrée de la clé ; contrôle des numéros de séquence importés ; procédure de révocation testée (politique de sécurité, section 6).

R4 — Exécution des générateurs de framework sur Rémus Moyenne

Impact grave · probabilité moyenne · fonctionnalité « modèles de framework »

Description. Pour reproduire exactement un projet Angular ou NestJS, Rémus exécute le générateur officiel (npx @angular/cli new, npx @nestjs/cli new) : du code téléchargé s'exécute dans le conteneur de Rémus, qui a accès au volume et donc à la clé de signature.

Scénario. Une version compromise d'un générateur est publiée ; une liste utilisant ce modèle la télécharge et l'exécute.

Risques encourus. Vol de la clé de signature (voir R3), des identifiants de dépôts privés, altération du stockage.

En place. Scripts d'installation désactivés pour toutes les autres résolutions ; conteneur sans privilège ; versions de générateur choisies par l'utilisateur. Recommandé. N'utiliser les modèles qu'avec des versions précises et éprouvées ; à terme, exécuter les générateurs dans un conteneur jetable sans accès au volume (évolution prévue).

R5 — Registres de Romulus accessibles sans authentification Moyenne

Impact grave · probabilité moyenne · choix assumé (ADR 0001)

Description. Comme un dépôt interne classique, npm, PyPI, Docker, apt, VS Code… sont lisibles par toute machine qui atteint Romulus, sans compte.

Risques encourus. Lecture de paquets issus des dépôts privés de l'organisation par toute personne du réseau isolé ; inventaire des logiciels utilisés.

Recommandé. Restreindre l'accès réseau à Romulus (pare-feu, VLAN) ; ne collecter de paquets privés que si leur diffusion à tout le réseau isolé est acceptable.

R6 — Double authentification facultative Moyenne

Impact grave · probabilité faible · choix assumé (ADR 0009)

Description. Les comptes, administrateurs compris, peuvent n'utiliser que le mot de passe, car les téléphones sont souvent interdits en zone isolée. Risques encourus. Un mot de passe administrateur deviné ou volé suffit à approuver un collecteur ou lever une interdiction. Recommandé. Activer la double authentification sur tous les comptes administrateurs (application ou clé TOTP matérielle), mots de passe longs et uniques.

R7 — Alertes de sécurité partielles et figées à l'export Moyenne

Impact important · probabilité moyenne · limite fonctionnelle

Description. Les alertes ne concernent ni Docker, ni Debian/RPM, ni Ansible, Terraform ou VS Code ; un paquet déjà exporté garde sur Romulus les alertes connues au moment de son export. Risques encourus. Fausse impression de sûreté ; une faille publiée après l'export n'apparaît pas sur Romulus. Recommandé. Export complet périodique ; consulter Rémus, à jour, avant de décider ; scanner dédié pour les images et paquets système. Une transmission incrémentale des alertes est à l'étude.

R8 — Données au repos non chiffrées Faible

Impact important · probabilité faible

Base SQLite (dont les secrets TOTP), clés et fichiers sont en clair dans le volume, protégés par les droits du système. Quiconque lit le disque ou une sauvegarde obtient ces éléments (pas les mots de passe, hachés). Recommandé. Chiffrement du disque et des sauvegardes.

R9 — Journaux non conservés par l'application Faible

Impact limité · probabilité moyenne

Le journal d'audit est écrit sur la sortie du conteneur ; sans collecte, il disparaît avec le conteneur et n'est pas protégé contre la modification. Recommandé. Collecte centralisée, conservation d'au moins six mois, alertes sur les refus répétés et les approbations de collecteur.

R10 — Lecture d'un contenu non vérifié avant la signature Faible

Impact important · probabilité faible

Pour afficher un bundle présent sur la clé USB, Romulus lit son manifeste JSON et les en-têtes de l'archive avant de pouvoir vérifier la signature. Un fichier forgé exploitant un défaut de cet analyseur pourrait affecter Romulus : écrit en PHP, sans gestion manuelle de la mémoire, il peut au pire échouer ou mal lire le fichier (déni de service). Le code d'analyse est restreint et testé ; rien n'est écrit avant vérification. Recommandé. Supports de transport contrôlés (voir politique de sécurité, 5.3).

R11 — Sources sans empreinte publiée Faible

Impact important · probabilité faible

Les rôles Ansible (archives GitHub) et certaines extensions VS Code n'ont pas de somme publiée : seule la connexion HTTPS garantit leur origine ; une fois collectés, leur empreinte est figée dans le bundle signé.

R12 — Blocage ciblé d'une connexion Faible

Impact limité · probabilité moyenne

La limitation des tentatives peut être déclenchée volontairement contre un identifiant depuis la même adresse IP (postes derrière un même NAT), bloquant sa connexion 15 minutes. Contournement : attendre, ou connexion depuis une autre adresse.

R13 — Styles en ligne autorisés par la CSP Faible

Impact limité · probabilité faible

La CSP de l'interface autorise style-src 'unsafe-inline', nécessaire aux styles des composants Angular. Une injection de balisage, déjà bloquée par Angular et Trusted Types pour les scripts, ne pourrait modifier que l'apparence.

R14 — Conteneur root en Docker rootless Faible

Impact limité · probabilité faible

En Docker rootless, le conteneur tourne avec l'UID 0, qui correspond à l'utilisateur sans privilège de l'hôte ; les capabilities CHOWN, DAC_OVERRIDE et FOWNER y sont effectives pour lire les volumes. Une évasion du conteneur donne les droits de cet utilisateur, pas ceux de root.

R15 — Composant vulnérable connu non exploitable Faible

Impact limité · probabilité faible

pip 26.3 embarque une copie de setuptools concernée par CVE-2025-47273 ; la fonction vulnérable n'est pas présente dans cette copie (exception documentée pour Trivy). Une ligne de base PHPStan masque des imprécisions de typage anciennes, sans faille connue ; elle ne peut que décroître (ADR 0008).

R16 — Code d'installation dans les journaux Faible

Impact important · probabilité faible

Tant qu'aucun compte n'existe, le code d'installation affiché dans les journaux permet de créer le premier administrateur. Une personne lisant les journaux à ce moment pourrait s'en emparer. Recommandé. Terminer l'installation aussitôt après le premier démarrage.

R17 — Configuration de VS Code par modification de son installation Faible

Impact limité · probabilité moyenne

VS Code de Microsoft ne se branche sur Romulus qu'en modifiant son product.json, ce que l'éditeur signale comme une installation modifiée et qu'une mise à jour annule. Les postes peuvent alors revenir vers la galerie publique, inaccessible depuis le réseau isolé. Recommandé. Préférer VSCodium ou code-server, configurés par variables d'environnement, ou automatiser la modification.
